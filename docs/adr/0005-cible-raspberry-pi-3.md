# La cible d'exécution est un Raspberry Pi 3, pas la machine de dev

Le code est développé sur macOS mais tourne sur un **Raspberry Pi 3 Model A+ Rev 1.0** (vérifié sur la machine via `/proc/device-tree/model` — hôte `babyphone.local`, Cortex-A53 aarch64, 512 Mo de RAM, Wi-Fi seul, un unique port USB occupé par le micro, stockage microSD, Raspberry Pi OS Bookworm / Python 3.11), démarré et arrêté à la demande par la domotique via SSH. Cette machine n'est pas un détail de déploiement : ses limites matérielles expliquent une bonne partie de la forme du code, et rien dans le dépôt ne les rend visibles.

Ce qui contraint directement la conception :

- **CPU modeste, budget temps réel dur.** Un bloc audio dure 50 ms ; tout le traitement d'un bloc (RMS, seuil, décision, émission) doit tenir dedans, sinon le flux audio déborde et produit des erreurs de lecture. Les chemins chauds — un calcul par bloc, 20 fois par seconde — doivent rester en C ou en O(log n) : médiane par fenêtre triée incrémentale, RMS via `audioop`. Toute régression de performance ici est un bug fonctionnel, pas un détail de style.
- **512 Mo de RAM, partagés avec l'OS.** Les structures permanentes se dimensionnent en dizaines de Ko (fenêtre d'amplitudes ≈ 100 Ko) ; conserver de l'audio brut en mémoire au-delà de quelques secondes n'est pas une option.
- **Les erreurs de lecture micro sont normales, pas exceptionnelles.** L'alimentation micro-USB du Pi 3 tolère mal les pointes de courant d'un micro USB : une sous-tension provoque des coupures du flux audio. C'est la raison d'être du comptage d'erreurs consécutives et de la réinitialisation avec retries de la source audio — le mode de panne dominant en production, à ne pas simplifier.
- **La détection du périphérique d'entrée est spécifique à la cible.** Le micro est choisi en cherchant « mic » ou « input » dans les noms de périphériques ALSA du Pi. Sur la machine de dev, l'heuristique tombe sur autre chose ou sur rien.
- **Wi-Fi seul (pas d'Ethernet sur le 3A+), coupures comprises.** Les envois vers la domotique doivent survivre à un lien qui tombe : timeouts bornés, retries, et jamais de blocage indéfini de la boucle d'écoute (la dette synchrone de [ADR-0003](0003-webhooks-domotique-sans-flux-audio.md) reste la principale faiblesse).
- **Aucun environnement virtuel n'est conservé dans le dépôt.** Un venv embarque des extensions compilées pour l'architecture qui l'a créé — `aarch64-linux-gnu` sur le Pi, incompatible macOS, et réciproquement. Chaque machine régénère le sien avec `uv sync` (dépendances verrouillées dans `uv.lock`, Python épinglé en 3.11 pour coller à Bookworm). Sur le Pi, la compilation de `pyaudio` demande `portaudio19-dev`, `python3-dev` et `gcc`.
- **`pyaudio` / `portaudio` ne se comportent pas pareil hors cible.** L'énumération des périphériques et le comportement du flux dépendent de la pile audio de la machine. La logique de décision est, elle, testable partout (module pur) ; tout ce qui touche à l'audio ou aux périphériques se valide sur le Pi.
